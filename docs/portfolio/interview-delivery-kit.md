# 产品经理面试交付包

> 版本：2026-08-07。适用于当前本地工作树。真实用户研究尚未执行，本材料只使用可复核的产品、方法和工程事实。

## 一句话定位

AI Hook Lab 不是“替用户写一句爆款文案”的生成器，而是一套帮助中文内容创作者围绕真实主题比较多个开头、作出选择、完成必要改写，并让后续 Prompt 决策可追溯的创作与评测工作台。

## 90 秒逐字稿

“这个项目解决的不是模型会不会写一句话，而是创作者面对同一个主题时，怎样更快比较不同开头并作出可复盘的选择。

首页默认是短路径：输入主题、平台和内容类型，生成十条候选。只有当简报不完整或用户要继续打磨时，才打开创作 Agent，避免把技术模式选择变成首屏负担。十条并不是已经证明的最佳数量，而是下一轮真实研究要比较的产品参数。

我没有把模型自评分当成用户效果。项目把真实用户、固定评测集和模拟数据分开，并实现了二十个主题乘三个平台的六十个固定案例、双人盲评、分歧裁决、Bad Case 复盘和七项升级门禁。即使完整 Mock 流程全部跑通，系统仍会阻止版本升级。

我还主动否决了两件事：不根据简历百分比反推数据，也不把密钥配置暴露给普通用户。当前真实创作者验证尚未执行，所以我不会声称采用率或传播提升。下一步是招募五到八名持续创作的人，累计至少三十个真实任务，先验证选择、改写和比较负担，再决定候选数量和 Prompt 是否值得升级。”

## 5 分钟展开版

### 0:00–0:45 问题与用户

- 目标用户是近一个月持续发布、已有真实选题、需要快速比较开头方案的中文内容创作者。
- 核心任务是“比较并决定”，不是“让模型替我写”。
- 第二类用户是复盘 Prompt、人工反馈与 Bad Case 的内容运营人员。

### 0:45–1:45 核心流程与取舍

- 经典生成保持默认，减少首屏认知负担；Agent 只在补全简报和继续打磨时介入。
- 一次展示十条候选以制造可比较差异，但明确把数量视为待验证参数。
- 收藏、最终选择、使用方式和实际发布分开记录，避免把弱意图写成采用。
- 无模型服务时返回安全错误并保留输入，不要求普通用户配置密钥。

### 1:45–2:50 评测与证据

- 固定评测集包含二十个主题、三个平台，共六十个案例。
- Baseline 与 Candidate 使用相同输入和参数，由两名评测员盲评，分歧交给第三人裁决。
- 七项门禁同时约束完整性、人工评测、来源、Bad Case 和安全；Mock 永久不能形成升级结论。
- `real_user`、`evaluation_set`、`simulation` 分别计算，对外数字必须有原始记录、口径、复算和审批。

### 2:50–3:40 异常、权限与治理

- 管理员、评测员、裁决员权限分离；评测员只看到匿名 A/B，不读取 Prompt 映射。
- 运营 Agent 只读，不能改 Prompt、发布版本或发送消息。
- 生产存储、安全错误、同源检查、配额和密钥扫描都有明确边界。

### 3:40–4:25 主动否决

- 否决根据简历百分比反向补造研究数据，因为这会破坏可复核性。
- 否决用模型自评分或 Mock 收藏证明用户价值，因为数据来源错误。
- 否决继续扩展新 Agent，把 P0 转向真实用户证据和主路径验收。

### 4:25–5:00 下一步

- 使用已准备的研究执行包和空白工作簿，招募五到八名创作者，每人至少三个真实任务，目标不少于三十个有效任务。
- 先建立任务完成、选择、改写、反馈覆盖和比较负担基线。
- 少于三十个有效任务只报告观察与整数计数；Prompt 升级还必须通过完整离线盲评和人工审批。

## 简历表述

### 一行版

围绕中文内容创作者的 Hook 候选比较任务，设计经典生成、可选创作 Agent、人工选择反馈与可复核评测闭环，并建立来源隔离、Bad Case 和 Prompt 升级门禁。

### 三条版

- 定义“真实主题输入—十条候选比较—最终选择—必要改写—使用方式确认”的核心任务，设计经典生成默认、Agent 按需介入和异常恢复路径。
- 设计并实现二十个主题 × 三个平台的六十个固定离线案例，覆盖双人盲评、第三人裁决、Bad Case 复盘、七项升级门禁和七类可追踪导出。
- 建立真实用户、固定评测集和模拟数据来源隔离及公开证据分级，阻止 Mock、模型自评分和未完成研究形成用户效果或版本升级结论。

### AI 协作说明

使用 AI 辅助生成部分代码、测试与文档初稿；本人负责目标用户、指标口径、产品取舍、权限和隐私边界、反例检查及最终验收。

### 禁止恢复的数字

真实用户人数、收藏率、最终选择率、实际发布采用率、离线提升百分比，在脱敏原始记录、整数分子分母、复算脚本和人工审批齐备前不得写入简历。研究计划中的“五到八人、至少三十个任务”只能描述未来计划，不能写成已完成结果。

## 高频面试问答

### 为什么做十条，而不是三条或五条？

当前十条来自产品假设：需要足够差异支持比较，但它不是已验证最优值。我会在真实任务中比较五条和十条的完成时间、最终选择、改写分布和一到五分的比较负担；样本不足时只看观察与整数计数。

### 为什么不让 Agent 成为默认入口？

目标用户通常已经有主题，默认对话会增加模式理解和追问成本。经典生成提供最短路径；只有简报缺失或需要继续打磨时，Agent 才创造额外价值。

### 为什么模型评分不能代表效果？

模型评分来自模型规则，不是用户行为，更不是发布结果。它可以解释和排序候选，但采用必须来自人工最终选择和使用方式，发布还需要单独授权回访。

### 六十个固定案例证明了什么？

它们证明评测输入、流程、角色、导出和门禁可复核，不证明真实用户喜欢候选，也不证明传播提升。只有完整双盲和裁决结果才能支持 Prompt 比较。

### 100% Mock 流程为什么仍不能升级？

因为它验证的是状态机和权限，不是真实样本质量。系统把执行模式和来源作为硬门禁，即使所有 Mock 评分都通过，报告仍保持“需要继续评测”。

### 你做过最重要的产品取舍是什么？

停止横向增加功能，把 P0 从“更多 Agent”转向“证据可信与主路径可恢复”。这直接改善了招聘可信度，也让下一步能回答用户是否愿意选择和改写，而不是继续堆功能。

### 你如何定义采用？

测试内最终选择、确认使用方式和实际发布是三个层级。任务级选择只表示本次比较的最后选择；确认采用来自直接使用、轻改或重写；实际发布只在获得回访授权并由参与者确认后计算。

### 如果真实研究没有改善怎么办？

先检查任务完成、反馈覆盖和排除原因，区分产品流程失败与候选质量失败。如果十条造成负担，优先测试减少默认展示或分组；如果主题锚定和平台语气反复失败，修 Prompt 并重新走离线盲评；不会选择性删除负面任务。

### AI 在项目里做了什么，你本人做了什么？

AI 帮助生成实现和材料初稿，也加速了测试补齐。我本人对问题定义、指标口径、取舍、权限隐私、反例和是否接受结果负责。面试中会展示被我否决的 AI 建议和最终验收门禁。

### 当前最大风险是什么？

真实目标用户证据仍为空白，线上版本也未与本地修改完成一致性验收。因此当前只适合陈述方法和实现，不适合宣称采用或业务效果。

## 演示失败兜底

| 失败 | 当场处理 | 不做什么 |
| --- | --- | --- |
| 在线地址打不开 | 立即切本地录屏或截图，继续讲产品判断 | 不反复刷新，不现场部署 |
| 模型服务不可用 | 展示安全错误和输入保留，再切候选截图 | 不展示密钥，不修改环境变量 |

| 面试官追问真实效果 | 明确回答尚未执行真实研究，展示研究计划 | 不用 Mock 或离线分数替代 |

## 面试前检查

- GitHub 首页、产品决策简报、评分卡和研究执行包可以离线打开。
- 准备一份 60–90 秒录屏、桌面截图、移动端截图和空白研究工作簿。
- 练习在 15 秒内说清目标用户和核心任务，在 20 秒内说清为何 Mock 不能升级。
- 删除浏览器中的密钥、个人账号、历史任务和参与者信息。
- 现场只展示已经复核的本地版本；部署状态和真实研究状态如实说明。
